# Technical Architecture & Design Decisions: Enterprise Hybrid-RAG Engine

This document outlines the architectural trade-offs, engineering decisions, and benchmark considerations made during the design and implementation of this hybrid Retrieval-Augmented Generation (RAG) system.

---

### 1. Architectural Choice: RAG vs. Fine-Tuning
* **Trade-off:** Fine-tuning modifies model weights to teach specific tone, style, or output structures, but it does not reliably update factual knowledge, is computationally expensive, suffers from catastrophic forgetting, and can still hallucinate.
* **Decision:** RAG decouples knowledge storage from generation. We can dynamically ingest, update, or purge documents in real time without retraining. Furthermore, RAG delivers auditable source attribution and strict access control per document.

---

### 2. Storage & Vector DB: PostgreSQL (`pgvector`) vs. Dedicated Vector Databases
* **Trade-off:** Dedicated vector databases (Pinecone, Milvus, Chroma) introduce separate billing, distributed transactional latency, network hops, and data synchronization drift between relational tables and vector indexes.
* **Decision:** Using PostgreSQL with the `pgvector` extension allows relational document metadata, audit timestamps, and 384-dimensional dense vectors to live within a single ACID-compliant database. Cascading foreign keys (`ondelete="CASCADE"`) guarantee that deleting a document cleans up all associated vector chunks immediately, preventing orphaned records.

---

### 3. Distance Metrics: Cosine Distance vs. Euclidean vs. Dot Product
* **Cosine Distance ($1 - \cos(\theta)$):** Measures angular orientation regardless of magnitude. In natural language processing, texts covering the same topic point in the same direction even if length varies.
* **Dot Product ($A \cdot B$):** Evaluates both orientation and magnitude.
* **Decision:** All embeddings generated by `all-MiniLM-L6-v2` are L2-normalized upon inference. When vectors are unit length ($|v| = 1$), Cosine Distance and Dot Product are mathematically equivalent. We utilize `pgvector`'s `<=>` cosine distance operator for clean, intuitive similarity scoring.

---

### 4. Vector Indexing: HNSW vs. IVFFlat
* **IVFFlat (Inverted File Flat):** Requires a training step on pre-existing vectors to establish cluster centroids. Recall degrades significantly as new embeddings are inserted without re-indexing.
* **HNSW (Hierarchical Navigable Small World):** A multi-layer graph-based index structure providing logarithmic search complexity and high recall without requiring training phases.
* **Decision:** Configured HNSW with `m = 16` and `ef_construction = 64`. This setup provides sub-millisecond nearest neighbor query latency while comfortably supporting real-time incremental document insertions.

---

### 5. Chunking Strategy & Overlap Tuning
* **Chunk Size (500 characters):** Small chunks (e.g. 100 chars) lose contextual meaning; overly large chunks (e.g. 2000+ chars) dilute semantic vector representations and increase token overhead. 500 characters balances high semantic specificity with adequate context.
* **Sliding Window Overlap (50 characters):** Eliminates boundary context loss. If a sentence or causal explanation spans across chunk boundaries, overlap ensures that both neighboring chunks contain enough context for retrieval.
* **Boundary-Aware Splitting:** Powered by LangChain's `RecursiveCharacterTextSplitter`, prioritizing natural semantic breaks (`\n\n`, `\n`, `" "`, `""`) and word boundaries over abrupt character cuts to preserve semantic cohesion.

---

### 6. Retrieval Strategy: Hybrid Search (Dense + Sparse Boost)
* **Problem:** Dense vector embeddings capture semantic concepts (e.g., "automobile" matches "vehicle"), but can fail to rank exact keywords, part numbers, error codes (e.g., `ERR_404_TIMEOUT`), or specific product IDs.
* **Decision:** Implemented a hybrid retrieval approach: dense vector retrieval finds top candidate contexts via cosine distance, while a sparse keyword matching layer boosts scores for chunks containing exact lexical hits.

---

### 7. Hallucination Mitigation & Output Reliability
* **Prompt Grounding:** Strict system prompts instruct the LLM to formulate responses exclusively using provided context chunks. If context is missing or insufficient, the model falls back to a deterministic refusal message.
* **Low Temperature:** Model temperature is locked at `0.1` to enforce deterministic, fact-bound generation rather than creative extrapolation.
* **Source Citations:** Prompt instructions enforce attribution by linking generated statements to specific document filenames and chunk indices.

---

### 8. Evaluation Methodology (RAGAS Alignment)
The pipeline is designed to be evaluated using key RAGAS metrics:
1. **Faithfulness:** Quantifies whether all claims in the generated response can be inferred directly from the context.
2. **Answer Relevance:** Measures how directly the response addresses the input query.
3. **Context Precision:** Ensures relevant context chunks are ranked higher in the retrieval list.
4. **Context Recall:** Validates that all factual information required to answer the query is captured within top-$k$.

---

### 9. Concurrency & Model Lifecycle: Singleton Pattern
* **Memory Management:** Neural sentence embedding models (such as `all-MiniLM-L6-v2`) require loading weights into memory. Instantiating a new model instance per API request would exhaust memory and cause massive request latency.
* **Decision:** Wrapped `SentenceTransformer` in a thread-safe Singleton pattern (`EmbeddingService`). The model is loaded once into memory during application startup and shared across concurrent FastAPI worker threads. Batch embedding is used during document ingestion (`batch_size=32`) to maximize throughput.

---

### 10. Framework Selection: Asynchronous FastAPI Architecture
* Built on Starlette and Pydantic v2, FastAPI provides native asynchronous request processing, automatic OpenAPI / Swagger documentation, and fast data validation.
* This is ideal for ML microservices that handle concurrent I/O operations (PostgreSQL queries, file processing, and external LLM API calls).

---

### 11. Edge Cases: Out-of-Domain Query Handling
* When an input query does not match any ingested knowledge, cosine similarity scores remain low (typically $< 0.35$).
* The system evaluates retrieved similarity thresholds and uses strict prompt constraints, safely notifying the user that the knowledge base lacks necessary data rather than synthesizing fabricated facts.

---

### 12. Connection Pooling & Database Resilience
* SQLAlchemy engine is configured with connection pooling (`pool_size=10`, `max_overflow=20`) and `pool_pre_ping=True`.
* `pool_pre_ping` validates connection vitality prior to executing queries, preventing disconnect errors after periods of inactivity. Requests use FastAPI's dependency injection (`Depends(get_db)`) to guarantee clean session closure.

---

### 13. Embedding Dimensionality & Resource Footprint
* `all-MiniLM-L6-v2` generates 384-dimensional vectors. Compared to 1536-dimensional alternatives, 384-d vectors consume 75% less RAM and disk space, build HNSW graphs significantly faster, and calculate vector distances with minimal CPU overhead, making it lightweight for containerized deployments.

---

### 14. Data Integrity: Cascading Deletions
* `DocumentChunk.document_id` includes `ForeignKey("documents.id", ondelete="CASCADE")`.
* Deleting a parent document automatically removes all associated chunks and cleans up the HNSW vector index nodes within an ACID transaction, eliminating orphan vectors.

---

### 15. Horizontal Scalability Roadmap (10M+ Documents)
To scale this architecture to tens of millions of documents:
1. **Read Replicas:** Deploy PostgreSQL with read replicas to distribute vector search query load.
2. **Embedding Cache:** Implement Redis caching for frequent queries and common question-answer pairs.
3. **Decoupled Ingestion Pipeline:** Separate ingestion from the API server using a message broker (RabbitMQ / Kafka / Celery), processing chunking and vector embeddings across distributed background workers.
4. **Partitioning:** Implement table partitioning by tenant or category to limit vector search scope.

---

### 16. LangChain Integration: LCEL & Pydantic Structured Output
* **Procedural vs. Declarative (LCEL):** Traditional RAG implementations use scattered procedural code to assemble prompts, invoke models, and parse strings. LangChain Expression Language (LCEL) formalizes this pipeline as a declarative, unified graph:
  $$\text{Pipeline} = \text{ChatPromptTemplate} \longrightarrow \text{ChatModel} \longrightarrow \text{PydanticOutputParser}$$
* **Structured Output Schema:** Rather than returning raw unformatted strings, the pipeline enforces a strongly-typed JSON schema (`StructuredRAGOutput`):
  - `answer`: Grounded synthesis string.
  - `confidence_score`: Metric from $0.0$ to $1.0$ expressing context grounding.
  - `citations`: List of verified references containing filename, chunk index, and verbatim quote excerpts.
  - `suggested_followups`: 3 intelligently generated questions enabling interactive user workflows.

---

### 17. Agentic RAG: Dynamic Tool Calling & ReAct Execution
* **Why Autonomous Agents:** Fixed RAG pipelines assume every user prompt is a document search query. Real-world users frequently ask metadata queries (*"How many files are indexed?"*), conversational prompts, or queries exceeding internal documents.
* **Specialized Tools:**
  1. `search_knowledge_base`: Hybrid cosine vector retrieval against PostgreSQL `pgvector`.
  2. `get_document_stats`: Live SQL query reporting total documents, chunks, and storage statistics.
  3. `web_search_fallback`: Live DuckDuckGo web search when context is absent from internal data.
* **Reasoning Traceability:** The agent records every step (`Thought`, `Tool Name`, `Tool Input`, `Tool Output`) before formulating the final answer, ensuring 100% transparency and auditability for enterprise compliance.
